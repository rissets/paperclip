# Data Sources Docker data plane

The optional Compose overlay adds ClickHouse, MinIO, Redis, and pgvector to the existing Paperclip Compose project. It overrides the db image while retaining the base Compose pgdata volume and PostgreSQL 17 major version. It does not create a second Paperclip database. It also defines an opt-in GPU inference profile for BAAI BGE-M3 embeddings and BGE reranking. In this host-runtime setup, Docker runs only the data services; the API and datasource worker run on the host so local `pi` and `codex` executables are available.

## Prepare secrets

Copy docker/.env.data-plane.example to docker/.env.data-plane. Set `BETTER_AUTH_SECRET` to the existing Paperclip instance value so authentication remains valid. Generate distinct values for the MinIO root password, MinIO app secret, ClickHouse password, and Redis password. On a VM without a supported NVIDIA GPU, set `OPENROUTER_API_KEY` in this local file to the gateway credential; never commit it. The configured aliases are `openrouter/text-embedding-3-small` and `openrouter/openrouter/cohere/rerank-v3.5`. Keep this file outside Git. The data plane publishes PostgreSQL, MinIO S3, ClickHouse HTTP, Redis, and the MinIO console on configurable loopback-only host ports so host processes can connect without exposing them to the network.

MinIO runs as a non-root user from the source release and commit pinned in docker/minio/Dockerfile. Its upstream community repository was archived and no longer publishes a pullable community container image. The build therefore follows the upstream source-build direction. This makes the image reproducible from a pinned source commit; it does not provide ongoing upstream security maintenance. Assign an owner to review MinIO security advisories and rebuild or replace the object store.

The one-shot initializer creates the fixed paperclip-data bucket, enables versioning, and creates a bucket-scoped application identity. Paperclip receives that identity. The MinIO root credentials are only passed to the initializer and MinIO server. To rotate an existing app secret, remove the user with the admin client, change the local env file, and recreate minio-init.

Small datasource uploads and the legacy multipart endpoint pass through the API to a private temporary file. For files at least 16 MiB, the UI creates a durable upload session and sends 16 MiB binary parts to the API, which relays each part to private MinIO multipart storage. The UI keeps the session ID in origin-scoped `localStorage`; after a reload or reopening the app in the same browser profile it asks the API which parts arrived and hashes those local file slices before resuming. Each part is idempotent for identical bytes and rejects a different retry; PostgreSQL advisory locks serialize competing writes to the same S3 part number across API processes while allowing different parts to upload concurrently. Completion sends an ordered SHA-256 manifest; the API checks it against stored part receipts, completes MinIO multipart, then streams the object to verify total size and whole-object SHA-256 before atomically creating the datasource and ingestion job. A missing object, size mismatch, or checksum mismatch prevents onboarding and the cleanup worker retries removal. Sessions reserve per-company file quota and expire after 24 hours. This API-relayed path keeps MinIO private and avoids buffering the full large file in the API process; each request is bounded to one part.

The resumable endpoints are `POST /api/companies/:companyId/data-source-upload-sessions`, `GET /api/companies/:companyId/data-source-upload-sessions/:id`, `PUT /api/companies/:companyId/data-source-upload-sessions/:id/parts/:partNumber` (`application/octet-stream`, one part per request), `POST /api/companies/:companyId/data-source-upload-sessions/:id/complete`, and `DELETE /api/companies/:companyId/data-source-upload-sessions/:id`. Every endpoint enforces company access and the datasource-management permission. Resume works in the same browser profile; another browser/device must restart its own upload session, and expired server reservations are reclaimed by cleanup.

### Structured-file quality and publication

File-backed CSV/TSV and XLSX onboarding profiles the full input, then streams typed rows into ClickHouse. Type-invalid rows are quarantined; CSV rows with a field count mismatch and XLSX rows wider than the profiled schema are also quarantined. Missing trailing XLSX cells are treated as empty/null. Quarantined rows are excluded from the queryable table, while the source file remains stored for operator review. Quality metadata reports source, valid/published, invalid/quarantined, null, type-violation, and duplicate counts. The datasource detail page shows those totals and up to five of the first 50 bounded quarantine references; a reference contains the source row number, affected column names, and reason, never the raw cell values.

Publication is rejected when invalid rows exceed 10% of source rows or duplicate primary-key rows exceed 5% of publishable rows. Below those thresholds, valid rows can be published; duplicates are reported but are not automatically removed. CSV worker checkpoints store both source position and inserted-row count, so resume continues correctly after skipped invalid rows. Legacy XLS and bounded in-memory compatibility paths do not have the same file-backed streaming guarantee. This is row-level quality handling; collection-level temporal overlap findings still require an explicit operator decision about append, replace, or upsert.

### External PostgreSQL schema identity

PostgreSQL onboarding reads the connected account's visible base tables from every non-system schema in `information_schema`; it does not assume that a table lives in `public` or in the session's `search_path`. Each discovered table keeps its physical `sourceSchema` alongside the bare table and column names. Semantic roles, table profiles, relationship endpoints, and generated query templates use `schema.table` identities so same-named tables in separate schemas do not overwrite or join to one another. Foreign-key discovery retains both endpoint schemas. Inferred name-based joins are accepted only for one unambiguous target, preferring an exact table match in the source schema.

The structured-query path and the SQL Playground's **Select 10** and **Count Rows** actions quote schema and table as separate identifiers (for example, `SELECT * FROM "geo"."provinsi" LIMIT 10`). Manual SQL in the Playground must also qualify a PostgreSQL table when it is outside the active `search_path`; `SELECT * FROM "provinsi"` can fail even when onboarding found `geo.provinsi`. Generated JEV query examples use the source dialect's identifier quoting. A table allowlist may use `schema.table`; a bare PostgreSQL table allowlist is accepted only when that name resolves uniquely in the configured schemas. Snapshot and onboarding-observation reads apply the same qualification check. MySQL and MariaDB continue to qualify tables with their database name and backtick quoting.

### Operator semantic mapping review

After a CSV/Excel or external database source is ready, a board operator can open a table in **Data Sources → datasource → table** and review its inferred metrics and dimensions. The UI sends `POST /api/companies/:companyId/data-sources/:dataSourceId/tables/:tableId/mapping-review`. It requires the datasource-management permission and a board user; agent API keys cannot approve mappings. Approval checks each metric and dimension against the inspected table schema. Corrections can change the semantic label, description, physical column, and metric aggregation, but the API accepts no SQL expression. It rejects missing columns, sensitive identity/contact columns, non-numeric metric fields except `count`, and duplicate normalized labels. Each correction preserves the former label as a synonym and is attributed to `user_defined`; approval records verified provenance. The table keeps a schema fingerprint, reviewer, revision, and the most recent 20 review events, while the activity log records the review decision.

A correction is rejected with HTTP 409 while an ingestion, snapshot, or embedding job for that datasource is active. If a schema vector chunk exists, the service rewrites its bounded content from the corrected physical bindings and clears its inline embedding. It retires the active vector-generation pointer, records the prior generation for rollback/retention, invalidates datasource query caches, and marks embeddings pending. The durable embedding reconciler then queues a fresh generation scoped to the semantic-mapping revision; fallback from local BGE to OpenRouter keeps that revision isolated while validating the provider's actual model identity. Retrieval uses lexical matching until the new generation has complete coverage and the worker atomically publishes its pointer. If there was no schema chunk yet, reindex creates one from the reviewed table model before embedding.

## Start the data plane

Run from the repository root:

~~~sh
cp docker/.env.data-plane.example docker/.env.data-plane
# Edit docker/.env.data-plane and set all required passwords.
docker compose --env-file docker/.env.data-plane -f docker/docker-compose.yml -f docker/docker-compose.data-plane.yml up -d --build
~~~

The `server` and `datasource-worker` services in the overlay use the opt-in `docker-app` profile and are not started by that command. Run Paperclip's API and worker on the host as described below. The API and worker must receive the same `PAPERCLIP_SECRETS_MASTER_KEY_FILE`, MinIO credentials, ClickHouse password, Redis password, and OpenRouter key as the data plane.

## Run the API and worker on the host

The runtime env template is `docker/.env.host-runtime.example`. Copy it to `docker/.env.host-runtime`, then set `BETTER_AUTH_SECRET`, `CLICKHOUSE_PASSWORD`, `REDIS_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `OPENROUTER_API_KEY` to the same values used by Compose. The template binds the host's `pi` and `codex` locations into `PATH`, points the application at loopback-published data services, and keeps BGE URLs empty so `RAG_EMBEDDING_PROVIDER=auto` can fall back to the configured OpenRouter gateway.

When moving an already initialized Compose instance to the host, copy its instance config and encryption key once. Replace `<server-container>` with the server container name from `docker ps`:

~~~sh
export PAPERCLIP_HOME="$HOME/.paperclip/datasource-host-runtime"
mkdir -p -m 700 "$PAPERCLIP_HOME/instances/default/secrets" "$PAPERCLIP_HOME/uploads"
docker cp <server-container>:/paperclip/instances/default/config.json "$PAPERCLIP_HOME/instances/default/config.json"
docker cp <server-container>:/paperclip/instances/default/secrets/master.key "$PAPERCLIP_HOME/instances/default/secrets/master.key"
chmod 600 "$PAPERCLIP_HOME/instances/default/config.json" "$PAPERCLIP_HOME/instances/default/secrets/master.key"
~~~

Set `PAPERCLIP_HOME`, `PAPERCLIP_CONFIG`, and `PAPERCLIP_SECRETS_MASTER_KEY_FILE` in the host env file to those paths. Copy the config and key before stopping the Docker server; the key must match the encrypted datasource credentials already stored in PostgreSQL.

Start the API in one terminal and the worker in another. In both terminals, source the private host env file first:

~~~sh
set -a
source docker/.env.host-runtime
set +a
pnpm dev
~~~

~~~sh
set -a
source docker/.env.host-runtime
set +a
pnpm --filter @paperclipai/server exec tsx src/datasource-worker.ts
~~~

Verify `http://localhost:3100/api/health` and `http://127.0.0.1:3102/health`. The worker uses `pi` from the host `PATH`; keep `DATASOURCE_EMBEDDED_WORKER_ENABLED=false` so only the standalone worker claims datasource jobs.

On an NVIDIA VM with the NVIDIA Container Toolkit installed, add `--profile gpu` to the command to start the pinned TEI BGE-M3 embedding and BGE-reranker-v2-m3 services. Without that profile, `RAG_EMBEDDING_PROVIDER=auto` tries the local BGE endpoint, then uses the OpenRouter-compatible gateway. Set `OPENROUTER_API_KEY` in the private env file to use gateway embeddings and reranking. If the gateway key is absent and local BGE is unavailable, ingestion still publishes parsed chunks with `embeddingStatus=unavailable`; retrieval remains lexical and never fabricates vectors. Reranking tries the local BGE service, then the configured gateway route, then the existing deterministic TypeSafe JEV ordering/answerability check. Both model responses must return one unique, in-range candidate index and a finite score for every submitted document; partial, duplicate, or malformed rankings are treated as unavailable and fall through to the next backend. That JEV fallback requires a minimum fraction of substantive query terms to match one passage and reports literal term coverage, not calibrated confidence. The custom gateway's `/rerank` transport has not been live-probed; unsupported responses fall back to JEV. Datasources record their active embedding space, so BGE and gateway generations can coexist during staged migration; query vectors are scoped to authorized sources using the same active space. Each chunk also records the space used. Durable reindex jobs fill a dimension-specific pgvector sidecar in bounded batches, verify exact coverage, then switch the datasource pointer and job receipt atomically. Operators can preview and confirm pruning of generations older than 90 days while active and rollback generations remain protected.

At startup, both the API and standalone datasource worker validate explicitly configured inference URLs, provider choice, model aliases, and BGE revision syntax. This is a local syntax check only: it does not require an API key, contact the gateway, probe GPU availability, or prove a provider's endpoint contract. Malformed values fail startup with the setting name but never echo credentials; absent optional inference dependencies leave lexical retrieval and the documented JEV fallback available.

The existing BETTER_AUTH_SECRET requirement in the base Compose file still applies to the optional Docker app profile. The database, ClickHouse, MinIO, and Redis health checks must pass before starting the host API and worker. The first MinIO source build downloads the pinned upstream commit and Go modules, so it needs outbound build access and time. Data-service ports bind to loopback only; defaults are PostgreSQL `127.0.0.1:15432` in the data-plane example, ClickHouse HTTP `127.0.0.1:18123`, MinIO S3 `127.0.0.1:19000`, Redis `127.0.0.1:16379`, and MinIO console `127.0.0.1:9001`.

AI Reasoning accepts the configured `OPENROUTER_API_KEY` as well as the existing `RISSET_API_KEY`/`OPENAI_API_KEY` settings. Remote JEV System One separately requires `TYPESAFE_API_KEY`; its endpoint and model can be set with `TYPESAFE_BASE_URL` and `DEFAULT_SYSTEMONE_MODEL`. Without that credential, JEV uses its local heuristic decisions and sends no unauthenticated provider request. The embedded JEV credential has been removed from source; rotate that previously committed credential at its provider.

The ClickHouse HTTP API is available to the host API at http://127.0.0.1:18123 (or inside the Compose network at http://clickhouse:8123). Company databases use the existing paperclip_<company-id> naming scheme. ClickHouse image, PostgreSQL/pgvector image, and Redis image are pinned to multi-architecture digests in Compose. MinIO and its admin client are built locally from pinned commits with a pinned Go builder image.

Collection correlation deploys actual ClickHouse views only when both related CSV/Excel tables are ready and have verified ClickHouse table identities. View names are deterministic and collection-scoped; output columns are qualified with source-table IDs to prevent duplicate names. Creation is limited to 100 views per collection pass. The collection profile records each view as deployed, unavailable, or not deployed, and SQL authorization/preview counts include deployed views only. A collection re-correlation drops obsolete views previously created under Paperclip's `pcv_<sha256>` namespace. Relationship analysis returns at most 100 first-row samples per table and five initial RAG chunks per document in windowed queries; it indexes candidate key columns instead of comparing every schema column pair. App-side analysis is capped at 500 tables, 500 documents, 20,000 candidate key pairs, 500 relationships, 1,000 document correlations, and 5,000 document/table correlations. The datasource landing page calculates collection/source/table/row/chunk counts in three grouped database queries rather than reading every table/chunk ID for every collection, and correlation reads only datasource semantic metadata rather than external connection configuration. These caps bound profile and application-memory growth; database work for windowed samples still depends on the underlying row counts and has not been load-benchmarked. Other source types remain relationship candidates until their ClickHouse snapshot semantics are explicitly supported.

Structured CSV/XLSX quality profiles preserve full-data temporal minimum and maximum per physical date/timestamp column. Collection correlation exposes `semanticProfile.temporalOverlapAnalysis` for ready CSV/Excel tables when the same table identity (normalized table name) or both an entity and metric match and the physical date-column name is the same. Each finding carries table/source IDs, the overlapping ISO time window, and the match reason; the analyzer caps the collection to 500 tables and 250 findings. These are review candidates only: overlapping periods do not prove duplicate rows and do not authorize merging or changing the source's append/replace/upsert policy. Old profiles with only aggregate temporal bounds mark analysis `limited`; schema names/semantic metadata that do not match conservatively can leave overlaps undetected.

## State and integration boundary

The API's embedded ingestion worker is disabled and a separate host process runs `pnpm --filter @paperclipai/server exec tsx src/datasource-worker.ts`. It runs independent single-flight loops: file ingestion, external snapshots, and embedding reindex poll every two seconds; the heavy external-query loop polls every 500 milliseconds. A long snapshot therefore does not block file ingestion or query-job polling in that process. Both ingestion loops claim PostgreSQL jobs with leases; snapshots leave the live datasource available and publish each selected table only after a complete staged ClickHouse load. The worker checks active-job cancellation every 500 milliseconds and aborts file-object streams, external snapshot page queries, active ClickHouse insert requests, and the onboarding pipeline at their next progress/checkpoint boundary. A queued file job is cancelled immediately; a running reprocess rolls back staged PostgreSQL state while preserving the previous published source. Cancellation is refused during the short publication stage. The loops use the same company-secret key, MinIO credentials, ClickHouse and Redis configuration. Poll failures retry; `http://127.0.0.1:3101/health` returns 503 until all four loops have completed a successful poll. SIGTERM aborts an active snapshot page query, ClickHouse insert request, or heavy external SQL through its driver signal and drains the loops. A forced kill leaves the running job lease to expire. Query outcomes are marked uncertain without automatic replay because lease expiry alone cannot prove the remote statement stopped. Large CSV retries resume from the last durable parser byte offset, committed row, delimiter, and ClickHouse batch index. The cursor is persisted only after a batch is acknowledged or reconciled; source/schema identity is checked before reuse, and a job-scoped table ID keeps retry batch names stable. XLSX retries still rescan their worksheet stream. Batch publication assembles a new table in groups of at most 100 batches per statement; the previously published table remains readable. A full forced-process-restart rehearsal against the complete Compose stack and cross-engine publication reconciliation are still open. Multiple workers can claim distinct jobs, but cross-engine publication is not yet qualified for replica scaling.

The API remains responsible for schema migration. The worker starts after API health and checks that the job table exists; it does not apply migrations. Local development retains the embedded worker unless `DATASOURCE_EMBEDDED_WORKER_ENABLED=false`. To run a standalone worker locally, use `pnpm --filter @paperclipai/server exec tsx src/datasource-worker.ts` with an external `DATABASE_URL`, the same Paperclip home/config and secret key, and an accessible file store. Do not run independent embedded PostgreSQL instances for API and worker.

The worker persists the current stage and bounded progress details in the PostgreSQL job row while it owns the lease. The datasource detail page polls and displays stages such as source download, CSV profiling, semantic mapping, ClickHouse insert, external snapshot scan/publish, document embedding, and vector write; large jobs include scanned/inserted row counts. Large CSV retries start at the exact byte after the last committed logical CSV record, so quoted newlines and multi-byte UTF-8 remain safe; earlier acknowledged ClickHouse batches are included in publish assembly without reparsing those source rows. An unacknowledged or partially inserted batch is replayed from its saved start offset and is skipped/replaced by its durable batch row-count receipt. The checkpoint is bound to the file fingerprint, column mapping, deterministic table ID, and job. Other file types still resume at the ClickHouse batch sink and rescan the parser input. Publish assembly sends no more than 100 known batches per SQL request and writes into a fresh stage before exchange. External snapshots checkpoint fully published table IDs: retries skip those tables and rescan only the incomplete table from its first keyset page; page-level cursor resume is not implemented. Full snapshots and incremental deltas are stored under job-and-attempt-scoped ClickHouse names. During a full refresh the existing snapshot pointer stays active until a lease-checked PostgreSQL transaction publishes the new pointer and receipt; a hard crash after exchange leaves a pending target receipt. The external-snapshot worker sweeps stale receipts after a five-minute grace period, drops only validated targets not referenced as the active base or delta, and clears metadata after successful cleanup. Sweeps are bounded to eight table rows and an eight-second ClickHouse cleanup budget; failures retry on a later poll.

API and worker share `paperclip-data` and the new `datasource-local-uploads` volume mounted at `/app/data/uploads`. **Before an existing deployment adopts this overlay**, back up and copy existing local originals into that volume while preserving their paths; mounting an empty volume hides files previously stored in the container layer. Host-local paths elsewhere require explicit relocation of files and stored paths, or equivalent mounts visible to both processes. New MinIO uploads require no disk-volume migration. Keep an existing non-default secret key by configuring `PAPERCLIP_SECRETS_MASTER_KEY_FILE` to its shared-volume path; never generate a replacement key for an existing database. Initial key creation publishes complete bytes atomically so concurrent processes read the winning key.

For a database that already has local datasource files, first copy/mount the old upload volume into the new shared upload volume while preserving every absolute `storage_path`, then run the migration from the repository's server build with the Compose env and datasource services available. The command is read-only by default. It accepts only ready/error file datasources without an active file-ingestion job, requires every path to resolve under an explicitly allowed root, rejects symlinked/non-regular files and recorded-size mismatches, streams SHA-256-verified bytes to deterministic company/source-scoped MinIO keys, then updates the PostgreSQL pointer with compare-and-set. It preserves the existing local file for rollback; rerunning after interruption reuses the same object key and checksum.

~~~sh
docker compose --env-file docker/.env.data-plane -f docker/docker-compose.yml -f docker/docker-compose.data-plane.yml \
  run --rm --no-deps --entrypoint node server \
  --import ./server/node_modules/tsx/dist/loader.mjs \
  server/dist/migrate-data-source-objects.js --root /app/data/uploads

# Review the dry-run summary, then run the same command with --apply.
docker compose --env-file docker/.env.data-plane -f docker/docker-compose.yml -f docker/docker-compose.data-plane.yml \
~~~

Run during a maintenance window after the old files have been copied into the mounted volume and before deleting old storage. Add `--root` for each additional absolute path prefix already recorded in the database. The command reports counts plus up to 100 sanitized source/stage failure details; post-copy failures and pointer conflicts also include the deterministic object key so an operator can check whether it is still referenced before cleanup. It never prints datasource contents, absolute paths, or credentials. Each successful pointer switch writes an activity-log record. Verify migrated datasource reads and checksum metadata before retiring the old local files.

### Agent-facing structured queries and table identity

The Data Agent's structured query CLI returns stable `tableId`, `dataSourceId`, numeric `rowCount`, and the published physical `clickhouseTable` in JSON catalog output. Use both IDs for `--aggregate` and `--describe-table` so those operations resolve the selected source directly instead of listing the full catalog again. Use the physical identifier for direct `--sql`; the displayed table name is a logical label and can differ from the ClickHouse table name. `system.tables` describes ClickHouse catalog entries, not records in a datasource; use `count()` on the physical table when a source-record count is required.

Agent SQL authorization is still evaluated against the agent's current datasource grants and deployed collection views. For assigned tables, the API accepts an unambiguous logical/display alias, sanitized legacy alias, or physical table identifier and rewrites references in `FROM`/`JOIN` clauses to the published physical name before execution. It does not rewrite comments or string literals, and CTE names are left alone. If one alias identifies multiple granted tables, it is not resolved implicitly; use the exact physical identifier. This compatibility mapping fixes logical-name queries without widening table access.

Structured `sum` and `avg` remain numeric-only. `count` counts non-null values; `min` and `max` accept numeric or date/time columns, including timestamp-like string columns. On ClickHouse, string timestamps are parsed with `parseDateTimeBestEffortOrNull` for these extrema; native ClickHouse date/time and numeric columns are used directly. Invalid functions, columns, or incompatible types return a validation error instead of surfacing as an internal server error.

The shipped Data Agent instructions direct a new analysis to list the catalog once, use stable IDs, choose bounded ClickHouse aggregation, distinguish source row counts from grouped-result counts, and avoid `SELECT *` or whole-dataset retrieval. A chart-only/presentation follow-up reuses the immediately preceding verified result; failed queries get at most one correction retry, while timed-out external queries should be narrowed or reported instead of looped. Existing built-in Data Agents receive default managed instructions only when the shipped entry is absent and no external/legacy instruction source or committed managed revision takes precedence; operator-authored entry files are preserved.

### Durable external query jobs

The existing `POST /api/companies/:companyId/data-sources/:id/query-sql` remains the short interactive path with its 15-second server-side deadline and client-disconnect cancellation. A caller can send a slower bounded read-only query asynchronously instead:

- `POST /api/companies/:companyId/data-sources/:id/query-jobs` with `sql`, optional scalar `params`, `rowLimit` (1–1,000), and `statementTimeoutMs` (1,000–60,000). It returns HTTP 202 with a job receipt and status/result URLs.
- `GET .../query-jobs/:jobId` reads status; `GET .../query-jobs/:jobId/result` returns the result after success; `POST .../query-jobs/:jobId/cancel` cancels queued work immediately or signals a running worker to cancel its active database statement.

PostgreSQL is the source of truth for the queue, actor provenance, SQL fingerprint, lease, cancellation state, bounded JSON result, and expiry. The SQL and parameter values are retained only while queued/running, then cleared; API responses never include the query text. Company-scoped advisory locking caps outstanding work at 10 jobs per source and 100 per company. Results are capped at 1 MiB and expire after one hour. The worker checks cancellation/deadline/lease ownership every 500 milliseconds. It shares the existing PostgreSQL protocol cancel and MySQL/MariaDB connection-destroy paths, and it uses the cross-process Redis source permit while executing. Redis remains an ephemeral concurrency control; a configured Redis outage fails the query closed.

Status and result reads re-check current company and agent-to-source access. A failed worker lease is terminalized as uncertain and is not automatically replayed; submit a new query job after checking the external database. Pending jobs survive API/worker restarts. Before execution, a local dialect-aware PostgreSQL/MySQL AST parser accepts one SELECT-backed query only and rejects write statements hidden in CTEs, SELECT INTO, row locks, multiple statements, and a denylist of known stateful/side-effecting built-in functions. Each driver then executes in a read-only transaction with statement/lock deadlines, and the SQL is wrapped in an outer LIMIT so an inner CTE limit cannot bypass the row cap. Keep external credentials read-only and least-privileged because custom SQL functions remain governed by the remote database's own grants. Snapshot and incremental unit/integration contracts are implemented; qualification against a real external database plus ClickHouse and a separate-process restart/cancel rehearsal remain acceptance work.

### Query and retrieval caches

Redis caches embeddings, bounded deterministic structured-query results, and RAG retrieval candidates. Structured results are cacheable only for ready CSV/Excel data already routed through the company ClickHouse table or an explicitly selected ready external snapshot; live external database results bypass the cache. Keys include company, current effective access scope, table/source revisions, snapshot timestamp, query shape, provider/model space where applicable, and retrieval filters. The default result/retrieval TTL is 60 seconds, capped at 300 seconds; query embeddings default to one hour. A cache hit still passes current source-grant checks, and the service re-reads source/table revision after lookup to reject a result racing publication. Redis outage or eviction degrades cache reads to misses; cache contents never grant job or authorization rights.

### External database snapshots

Board operators can queue a full snapshot at `POST /api/companies/:companyId/data-sources/:id/snapshot`. It accepts `{ "mode": "full", "tableIds": ["..."] }`; omitting `tableIds` selects all inspected tables with exactly one primary-key column. Tables without a single-column key are skipped and counted, and explicitly selecting one rejects the request. A job is limited to 100 tables and refuses another active ingestion/snapshot job for the same source. The route records an activity-log entry in the enqueue transaction. Full snapshots scan every selected row, compact any incremental deltas into the base ClickHouse table, and reconcile hard deletes that occurred in the source.

Each table is read from the external database in 2,000-row keyset pages ordered by its primary key, using only inspected column names, allowlisted source table/schema metadata, read-only transactions, and a 30-second statement deadline per page. MySQL keyset cursors preserve BIGINT values as strings. Before streaming begins, PostgreSQL records the attempt-specific ClickHouse target and deterministic stage-table name; a SIGKILL during upload therefore leaves enough metadata for later cleanup. The worker streams pages to that ClickHouse staging table. Before exchange, PostgreSQL changes the marker to `publishing`; a valid job lease is then row-locked through the ClickHouse exchange and receipt update. During a refresh, readers continue using the prior ready snapshot. If the process dies during streaming or between exchange and receipt, that prior pointer remains active and the unreferenced target/stage is eligible for cleanup after a guarded five-minute grace period. The sweeper considers at most eight rows and spends at most eight seconds on ClickHouse cleanup in one pass; any failed drop keeps the metadata for a later retry. When there was no prior snapshot, the table remains unavailable until retry completes. A retry skips tables already present in the job's published-table checkpoint and rescans an incomplete table from its first page. Real PostgreSQL + ClickHouse integration verifies recovery from a failure injected after table exchange, bootstrap retry, and a later incremental update/soft delete. A separate subprocess integration SIGKILLs a real worker after ClickHouse accepts a streamed insert, verifies the previous pointer remains queryable while a partial stage exists, expires the lease, and checks that a replacement worker cleans the abandoned attempt and publishes all 20,000 rows on attempt two. This qualifies the focused PostgreSQL + ClickHouse takeover path; a forced restart of the complete Compose stack and multi-replica cross-engine publication remain open. File byte counts and table row counts use PostgreSQL `bigint`; JavaScript-facing row counts must remain within the safe-integer range.

An operator can also queue a timestamp-based incremental sync for one or more selected tables. The request shape is `{ "mode": "incremental", "tableIds": ["<table-id>"], "tablePolicies": [{ "tableId": "<table-id>", "updatedAtColumn": "updated_at", "deletedAtColumn": "deleted_at" }] }`. Each table needs an inspected single-column primary key and an inspected date/timestamp `updatedAtColumn`; the optional `deletedAtColumn` must also be an inspected date/timestamp. The first incremental request for a table bootstraps it with a full keyset scan. Later requests read rows whose effective change timestamp is at or after the saved watermark minus a one-second overlap, ordered by effective change timestamp and primary key. The effective timestamp is `max(updatedAtColumn, deletedAtColumn)` when a tombstone column is configured, so a soft delete is captured even when the source does not also advance `updated_at`. The SQL projection returns an exact text cursor for that timestamp; this avoids driver `Date` millisecond truncation causing a repeated page or a skipped row when the source timestamp has microsecond precision.

Each non-empty incremental run writes a new immutable ClickHouse delta table. The publication transaction holds and verifies the PostgreSQL job lease, exchanges the staged delta table, then atomically publishes its pointer and new watermark in the table semantic model. The exact row count changes by joining only this delta's primary keys against the previous logical snapshot instead of recounting every row on each sync. Queries union the base and at most 32 referenced delta tables, choose the highest sync version per primary key, then remove tombstones; they do not depend on asynchronous `ReplacingMergeTree` merges. A full snapshot compacts those rows back into the base, clears the delta pointers, and drops the superseded delta tables after publication. Once 32 deltas are active, the API asks the operator to run a full snapshot before another incremental job. An empty run advances only the durable job receipt; it does not create a delta pointer.

Timestamp polling is `best_effort_updated_at`, not a transactionally consistent remote snapshot or CDC. It can miss a change that arrives with an old timestamp outside the one-second overlap, so source timestamp discipline matters and operators should schedule full reconciliation snapshots. A configured tombstone column handles soft deletes only when the source preserves a tombstone row; hard deletes remain visible until a full snapshot. The worker stores `deleteSemantics` and the watermark in the semantic model and query-source metadata so AI responses can surface freshness and deletion caveats. UI structured queries keep using the live external database by default; the operator can explicitly choose the ClickHouse snapshot. The built-in Data Agent automatically selects a ready snapshot for aggregate requests against external tables with estimated row counts of at least 100,000 unless the question asks for recent/current/live data. Its response includes the snapshot timestamp and consistency caveat. Page-level cursor resume for a single interrupted table and multi-host ClickHouse fencing remain follow-up work.

Worker lifecycle tests cover single-flight polling, failure recovery and drain. A real subprocess test with temporary PostgreSQL verifies health, durable job claiming and terminal failure for a persisted file-ingestion job whose staged file is absent, then clean SIGTERM exit; it does not qualify extraction/inference. Filesystem tests simulate concurrent master-key publication and preserve an existing key. The disposable Compose acceptance harness is `scripts/verify-datasource-data-plane.py`; it checks PostgreSQL+pgvector, ClickHouse aggregation, Redis TTL/noeviction, and MinIO application-scope/versioning CRUD without logging credentials.

## Enterprise Orchestration, Query Learning & Controlled Rollout

The Enterprise Orchestrator (`EnterpriseOrchestratorService`) coordinates natural language queries across structured CSV/Excel tables, external relational databases, and analytical ClickHouse snapshots.

### Controlled Rollout & Configuration
- **Agent Orchestration Mode:** Configured per-agent in **Agents → [Agent] → Data Sources** tab as Auto or Off (`agent.metadata.datasourceOrchestration.mode`).
  - `auto`: Heartbeat preflight resolves the agent's effective grants and query lane, then injects trace, table hints, and orchestration guidance into the Pi run. Non-data greetings skip schema retrieval; no sub-10ms latency claim is made.
  - `off`: Directly bypasses the orchestrator preflight.
- **Rollback Invariant:** Disabling orchestration (setting mode to `off`) or revoking data source access instantly disables coordinator lanes and stops experience reuse without deleting any tables, artifacts, or vector sidecars.

### Agent query flow and current boundary

For an Auto-mode data question, the heartbeat resolves effective source grants and calls `resolveQueryContext` before Pi runs. The adapter injects the selected lane, trace ID, accessible table hints, and an instruction to call `query_structured.py --orchestrate "<complete question>"`. That CLI submits `POST /api/companies/:companyId/orchestrator/query-executions`; `EnterpriseOrchestratorService.createQueryExecution` applies authorization, cache/template/experience routing, the question deadline, and the selected ClickHouse snapshot or live external query path. `query_database.py --orchestrate` submits to the same endpoint. Preflight by itself does not execute the analysis: Pi must invoke the CLI, so browser/run-trace verification is still required before claiming the whole interaction is accepted. The agent guidance makes this the default and forbids preliminary duplicate catalog/query calls. Document-only RAG still uses `search_knowledge.py`; mixed questions combine structured results with separately retrieved document evidence.

Each durable execution now stores the sorted datasource IDs authorized for that run in `data_source_query_executions.data_source_ids`; the GIN index supports source-filtered history. `GET /api/companies/:companyId/orchestrator/query-executions?dataSourceId=...&limit=...` returns at most 100 recent summaries and does not include result rows. `GET /.../query-executions/:id` returns the execution result. For agent callers, list, result, cancel, and feedback requests require the execution to belong to that agent and every captured datasource grant to remain active; rows without provenance fail closed for agents. Board callers are also limited by datasource RBAC where applicable. The datasource detail page shows status, engine, duration, summary/error, trace ID, and lets an operator mark the answer correct or submit a correction note. Feedback posts to `/.../orchestrator/query-executions/:id/feedback` and flows into the existing experience feedback recorder; it does not automatically promote a candidate to a reusable template.

### Structured query binding and safe fallback

Before execution, the coordinator intersects requested datasource IDs with the agent's current grants and resolves requested table references against that scoped catalog. Exact table IDs and schema-qualified names are preferred. A generic planner placeholder such as `table` is accepted only when it has one authorized candidate; unresolved or multiple candidates do not become a broad catalog search. The selected table IDs are passed to `DataAgentService`, which restricts its source and table inventory to that set. A structured local file query also requires a ready ClickHouse publication; when the selected table has no published snapshot, the coordinator returns an explicit not-ready result instead of running an unbounded or unrelated query path.

Metric labels and dimensions in the semantic model are bound back to physical columns in the inspected schema. A grouping request such as “per site” may use a verified dimension name or synonym; an unknown or ambiguous group-by field is rejected before aggregation. Explicit month requests use a half-open date range on the one verified temporal column, including Excel serial columns when their encoding or observed range proves that representation. Ambiguous temporal columns or an unknown numeric date encoding cause the agent to abstain rather than omit the requested period. External source execution records its actual engine (`postgres`, `mysql`, or `mariadb`) so routing and telemetry do not mislabel non-Postgres connections. Contract tests cover the date, metric, dimension, source/table scope, grant-denial, and unpublished-snapshot cases. These tests do not replace a successful browser-to-Pi query or measured latency qualification.

The 8 October 2026 DAT-14 browser check exposed two structured-query defects. Dimension matching previously scanned the entire prompt after a `per`/`group by` cue, so a dimension named only in a later “do not select” instruction could make the group-by appear ambiguous. Matching now stops at sentence, prohibition, and execution-context boundaries. The same run exposed that the planner emits `COUNT(*)`, while `queryTable` required every aggregate argument to be a schema column; `COUNT(*)` is now accepted only for `count`, translated to ClickHouse `count()` or SQL `COUNT(*)`, and returned under the stable `count_all` alias. Focused tests cover both cases. In the authenticated browser run DAT-16, the coordinator completed the count grouped by `domain` against `22_demo_incident_scenarios_truth_table`; the answer showed five groups totaling five rows, named the source/table, and included the orchestrator trace. The Agent Data turn finished in 22 seconds with one tool call; the coordinator execution itself took 105 ms. The execution record captures the agent's 34-source grant scope, while its result identifies the exact selected table. This verifies one small fixture below one minute but does not establish representative latency or a p95 benchmark.

### Onboarding semantic mapping and model runtime

Onboarding uses the configured ingestion specialist's model, instruction path, and adapter type. For `pi_local`, `AiReasoningService` starts the host Pi CLI first with `--no-session --no-extensions --no-tools`; it passes the bounded instruction file contents as the system prompt and expects validated JSON. A configured Router HTTP credential is used only if that Pi invocation fails, and the selected backend is included in onboarding reasoning steps. Other adapter types retain Router-first inference with Pi as fallback. Parsing, catalog discovery, row profiling, validation, embeddings, checkpoints, and publication remain server/worker operations; Pi does not connect directly to the source database.

- **CSV/Excel structured sources:** the parser profiles all rows through the bounded ingestion pipeline. Semantic table mapping receives the table's profiled columns and at most five sample rows, once per table. The semantic model proposes labels, metrics, dimensions, and queries; server-side validators and ClickHouse ingestion determine what is published.
- **Document RAG:** chunking and embedding happen in the ingestion pipeline. The knowledge specialist receives at most the first ten chunk samples for document-level domain/entities/topics/summary analysis; it does not embed every chunk in one LLM call. Vector writes are batched separately.
- **External relational databases:** a durable worker checks connectivity, discovers catalog/schema, profiles columns, maps tables, verifies relations, then publishes. Initial mapping is one JSON request per schema-qualified table/column batch, capped at 20 columns; every column and explicit FK target is supplied with at most three bounded sample values plus sampled distinct/null rates. Primary/foreign keys, identifiers, Indonesian name/identity/contact fields (such as `nama`, `NIK`, `KTP`, and `NPWP`), credentials, and other sensitive columns are redacted before model inference; email/phone/UUID-like values in other columns are also masked, and sample text is treated as untrusted data. If a validated mapping needs evidence for an ambiguous field, it may request at most four exact catalog columns that are not keys or sensitive fields. The worker builds the query itself from inspected identifiers, reads only those columns with `LIMIT 8` and a five-second statement timeout, then makes one final mapping call with those samples; that final call cannot request another observation. The model never supplies SQL, and cancellation applies to both the source read and inference. If observation fails or times out, the batch follows its existing deterministic fallback path rather than checkpointing an unvalidated answer. Raw observation rows are not saved as checkpoint artifacts; only the validated semantic mapping is eligible for checkpointing. Model role/profile keys, FK labels, schema chunks, and coverage metadata retain schema-qualified identity, preventing same-named tables in separate schemas from overwriting each other's semantic mapping. Results from later batches are merged and repeated entities/topics/query templates are deduplicated. Each validated result is saved in `data_source_job_checkpoints` under the job, table/batch fingerprint, and mapping-input fingerprint before it is applied. The fingerprint covers source database identity, row count/schema/FK targets, adapter/model, instruction path, and SHA-256 of the exact instruction content frozen at job start. The upsert is lease-fenced and idempotent, each payload is capped at 128 KiB, and a retry loads one batch at a time so large schemas do not accumulate all checkpoint payloads in memory. Input or instruction changes invalidate old mapping output. Each batch has up to a 30-second inference budget, each table has a 90-second total mapping budget, and each request allows at most two validation iterations; exhausted or invalid batches retain deterministic catalog metadata and publish explicit complete/partial/fallback coverage. Invalid best-effort model output is not checkpointed. The worker cancellation signal reaches local Pi/Router inference and prevents fallback after cancellation. When the worker marks the job succeeded, it removes these retry-only checkpoints in the same database transaction.

This is a bounded application-controlled observation cycle, not an autonomous Pi agent with arbitrary datasource tools. PostgreSQL checkpoint tests prove batch reuse across worker attempts, lease fencing, idempotent replacement, schema/instruction fingerprint isolation, checkpoint cleanup on owned success, and table-budget boundaries; focused tests also cover observation request validation and safe query construction. They do not prove real process-kill recovery through the full onboarding publication pipeline. No live Pi/provider, source-drift, restart, or browser run has yet qualified the path, and these code-level contracts do not establish end-to-end latency or mapping accuracy.

### Query Deadlines & Bounded Resource Pools
- **55-Second Whole-Question Ceiling:** All orchestrated query executions enforce a strict 55s ceiling (`QuestionDeadlineBudget`). 12 seconds are reserved for response formatting and network transport.
- **Dynamic Statement Timeout:** Database query timeouts are derived dynamically (`Math.min(20_000, remaining - reserve)`).
- **Corrective Retries:** At most 1 retry is permitted, and only if remaining question budget exceeds 15 seconds. Uncertain/timed-out operations are never replayed.
- **Connection Pools & Driver Cancellation:** External pools are bounded per source. Client disconnections or budget timeouts trigger driver cancellation (`activeQuery.cancel()` in Postgres, connection destruction in MySQL/MariaDB). Passwords are hashed with SHA-256; rotation immediately tears down stale pools.

### ClickHouse Dedup & Snapshot Workload
- **ReplacingMergeTree with FINAL:** Snapshotted external tables with primary keys use `ReplacingMergeTree` with a version column and `FINAL` injection in analytical SQL to ensure aggregate correctness across duplicate/updated rows.

### Query Learning, Experience Memory & Feedback
- **Candidate Isolation:** Successful queries are recorded in `data_source_query_experiences` with `status: "candidate"`. Candidates are **never reused** until verified.
- **Verification Gates:** An experience is only promoted to `user_approved` or `reference_verified` after passing reference benchmark SQL or operator review in the UI.
- **Schema Drift Guard:** Each experience records a SHA-256 schema fingerprint. Any structural change to referenced tables, columns, or metrics prevents outdated template reuse.
- **Negative Feedback Invalidation:** Submitting negative feedback (`needs_correction`) immediately marks the experience as `rejected` and purges it from candidate reuse.
